## Deviations from SPEC.md

- Commit order: the warehouse (spec item 11) and loaders (spec item 12) land before the fixture world and authorization cases (spec item 10), because `pv fixtures build` loads a DuckDB through the real loaders and dbt.
- The SCD2 snapshot uses `strategy: check` over the attribute columns (org unit, level, title, manager key, status, location) instead of `timestamp` on `export_date`: with every employee in every weekly export, a timestamp on the export date would version every employee every week. The history input is an ephemeral, pseudonymous model, so the snapshot holds no direct identifiers.
- Policy tags in schema YAML use `{{ var('pv_policy_tags')['<class>'] }}` directly: dbt does not expose project macros when rendering schema YAML (checked: "'pv_policy_tag' is undefined"), so the `pv_policy_tag()` macro was dropped.
- dbt staging models are ephemeral (no staging relations exist), so `var('pv_snapshot_export_date')` applies when each `dbt snapshot` of the replay compiles.
- Executor task ids are `<instanceId>:erase` and `<instanceId>:identity` (equal to `<requestId>:...` for the first attempt), so a retry instance gets fresh tasks; `loadSubject` falls back to the request's latest erase payload.
- Eval faults and variants are planted in R2, KV and D1 through Miniflare's own storage API with wrangler's persistence root (`scripts/eval-plant.ts`), because `wrangler r2 object put` cannot set custom metadata (needed for the custom-metadata fault); the oracle still reads D1 and KV through `wrangler --local` and R2 from the state files.
- Retention request ids are `<runId>-<12 characters of the subject_ref>` (Workflow instance ids allow only letters, digits, `-` and `_`).
- Iceberg snapshot ids travel as strings in executor results (they exceed JavaScript's safe integer range).
- Probe findings redact token occurrences inside locations (for example an R2 key named after an employee id becomes `[redacted]`), so findings stored in D1 never carry a value.
- The local `kv_propagation` residual is recorded as `cleared` with evidence `modeled` (there is no edge network locally).
- Purpose table functions read only their own purpose dataset's views (which are authorized on the source datasets), so no routine authorization on `pv_core` is needed; the generated BigQuery SQL has no dataset `AccessEntry` of type `ROUTINE`.

- Policy action `read_legal_holds` added for `GET /api/v1/privacy/legal-holds` (the spec's Action list had no read action for holds; it is granted to `privacy_officer` under `legal_hold_management` only).
- `AssetDef.parts` is a list of part objects (name, location, format, reference columns, retention) instead of plain strings, so per-part retention and reference columns live in the policy; `referenceColumns` is kept at asset level as the union.
- The HRIS weekly export is a full "all workers" snapshot (all 1,200 employees with their status in each of the 13 objects), so terminated subjects have source-export rows to erase. Retention-relevant dates of the held subjects are chosen so that past-retention objects split into deletions and minimizations (golden: 3 deleted, 5 minimized).
- Named queries carry structured filters (`eq`, `in_array`, `prefix_any_ci`) instead of SQL fragments, so the compiler emits each dialect itself.
- Commit order: the production commit (spec item 24) comes before the CI commit (spec item 23), so CI lands together with the committed eval results it gates on.
- The production eval profile runs no retention sweep (the spec's prod column says "not run" for R); it plants faults directly in production stores and removes them afterwards, and it runs once per seeded project.
